# M1.10 — VAT tax invoices and the VAT return draft (plan)

Goal: every sales and purchase document carries a **tax code per line** (decision A10, `domain-model.md` → Tax), a
**price mode** (VAT-exclusive, VAT-inclusive, no VAT with a reason), VAT per line rounded half-up to the fils with
the total = Σ lines (A3); a sales invoice prints as a **tax invoice** or **simplified tax invoice** in English and
Arabic; and a **VAT return draft** (VAT 201) is built from the posted lines, Box 1 split by the emirate of the branch
that made the supply, every figure drilling down to its documents.

Roadmap acceptance: the invoice PDF shows TRNs, Arabic, line and total VAT; Σ line VAT = total; the VAT return draft
drills down to documents. Proving tests: rounding property test; template snapshot tests (en/ar); box mapping tests
per tax code; credit-note period test. VAT round-off (L4) stays **off** until R4 is answered.

## M1.10a — tax codes and line tax

**Tax codes** (a fixed registry per country, businesses cannot edit rates; `seeds/tax_codes/ae.json`):

| Code | Side | Rate | Recoverable | Posting | VAT 201 |
| --- | --- | --- | --- | --- | --- |
| SR | sales | 5 | — | Cr vat_output (rule 1) | Box 1 (branch emirate): net + VAT |
| ZR | sales | 0 | — | no VAT line (rule 31) | Box 4: net |
| EX | sales | 0 | — | no VAT line | Box 5: net |
| OS | sales | 0 | — | no VAT line | not reported |
| SR | purchase | 5 | yes | Dr vat_input (rule 8) | Box 9: net + VAT |
| SR-B | purchase | 5 | no | VAT added to the expense line (rule 8) | not reported |
| ZR, EX, OS | purchase | 0 | — | no VAT line | not reported |
| RC-S | purchase | 5 | yes | supplier owed net; Dr vat_input / Cr vat_output (rule 29) | Box 3 (VAT due) and Box 10 |
| RC-G | purchase | 5 | yes | as RC-S (rule 30) | Box 6 (pre-filled by Customs; kept to check it) and Box 10 |

**Defaults per line:** the party's override if set (e.g. an export customer → ZR, an overseas service supplier →
RC-S), else the product's (`sales_tax_code`, `purchase_tax_code`; default SR), else SR. A business that is **not
VAT-registered** charges no VAT: every sales line is OS and nothing posts to VAT; its sales invoice is an "Invoice",
not a tax invoice.

**Price mode** on the document (`price_mode`: `vat_exclusive` default from the setting `sales.default_price_mode`,
`vat_inclusive`, `no_vat` + `no_vat_reason`: `zero_rated` → ZR, `exempt` → EX, `out_of_scope` → OS on every
line). Inclusive (open question R6, default): `VAT = round_half_up(gross × rate / (100 + rate), 0.01)`,
`net = gross − VAT` — so net + VAT is exactly what was typed. Exclusive: `VAT = round_half_up(net × rate / 100,
0.01)`. Prices stay stored per unit as typed with the mode; minimum and list prices (VAT-exclusive) are compared on
the net.

**Lines:** `document_line.tax_code` (new), `net_amount`, `vat_rate` and `vat_amount` kept (the rate
now comes from the code). The API still accepts `vat_rate` for one release where no tax code is given (5 → SR, 0 →
ZR on sales / OS on purchases) so older clients keep working until M1.10d.

**Blocked input VAT (SR-B)** is allowed on expense lines, service and non-stock purchase lines, and expense
vouchers; refused on stock lines (open question R8, default) because it would change the average cost.

**Invoice kind** on a posted sales invoice and credit note (`invoice_kind`): `tax_invoice` when the customer has a TRN,
`simplified` when not (open question R7, default; setting `vat.simplified_for_unregistered`, on). Recorded at post so
reprints never change.

**Existing rows** (pilot data only): lines with VAT 5 get SR; lines with VAT 0 get ZR (sales) or OS (purchases);
documents get `vat_exclusive`.

Tests: rounding property test (Hypothesis: Σ line VAT = tax_total for exclusive and inclusive; inclusive net + VAT
= gross per line; posting balances); posting per tax code (SR, ZR, EX, OS, SR-B, RC-S, RC-G); defaults from party over
product; no-VAT reason required; a non-registered business posts no VAT; old `vat_rate` input mapping; tenant
isolation for any new tenant table.

## M1.10b — VAT return draft

Box definitions seeded with the codes (`vat_return_box`: box, label en/ar, kind `amount_vat`, `amount`, `total`,
`manual`). Box 1 has seven lines, one per emirate: 1a Abu Dhabi, 1b Dubai, 1c Sharjah, 1d Ajman, 1e Umm Al Quwain,
1f Ras Al Khaimah, 1g Fujairah (R3: to be checked against the live EmaraTax form by the accountant). Boxes 8 and 11–14
are totals; Box 2 (tourist refunds) is not used; Box 7 and the Adjustments column are manual and wait for Phase 2.

`GET /vat-returns/draft?business_id&from&to` builds every box from posted sales and purchase lines and vouchers by
their tax code, dated in the period: a credit note or return reduces the original sale's box **in its own period**
(not the invoice's); cancelled documents are excluded, reversals count in their own period.
`GET /vat-returns/draft/lines?box=` lists the documents behind one figure (number, date, party, net, VAT) — the
drill-down. Saving and filing (which locks the period) come with Phase 2; this milestone is the draft.

Tests: box mapping per tax code; emirate split by branch (not the customer's emirate); credit note in a later period
reduces that period; cancelled invoice gone, reversal counted; totals boxes; drill-down sums equal the box.

## M1.10c — invoice templates

ADR 0012 decides how PDFs are made. Proposal: the API renders HTML (Jinja2 templates in `apps/api/app/modules/
documents/templates/`, English and Arabic side by side as UAE invoices usually are), and Chromium turns it into a PDF
— Electron's `printToPDF` on the desktop, the browser's print on the web. Alternatives: WeasyPrint in the API (needs
GTK on Windows, hard to bundle) and headless Chromium in the API (large). Arabic shaping and RTL are exact in
Chromium.

The tax invoice shows: "Tax Invoice / فاتورة ضريبية" (or "Simplified Tax Invoice"), supplier name, address and TRN,
customer name, address and TRN, invoice number and date, date of supply when different, per line description,
quantity, unit, unit price, net, VAT rate, VAT amount, line total; totals net, VAT, total in AED. Credit notes name the
original invoice. Snapshot tests per template (en/ar), and a test that Σ line VAT printed = total VAT printed.

## Open questions (written to `docs/open-questions.md`, defaults built and marked)

- **R6** — VAT-inclusive prices: VAT per line = gross × 5/105 rounded half-up, net = gross − VAT.
- **R7** — Simplified tax invoice: issued when the customer has no TRN; a registered customer always gets a full tax
  invoice (the law also allows simplified up to AED 10,000; e-invoicing removes simplified invoices later).
- **R8** — Blocked input VAT (SR-B) only on expenses and non-stock lines, never on stock.

## Built — M1.10a (tax codes and line tax)

- **Registry, not a table:** `seeds/tax_codes/ae.json` read by `app/modules/tax/codes.py` (codes, treatments, VAT 201
  boxes, `split` for exclusive / inclusive maths, `resolve` for defaults). Read-only and offline; lines store the code
  and the rate charged. `domain-model.md` → Tax updated.
- **Masters:** `product.sales_tax_code` / `purchase_tax_code`, `party.sales_tax_code` / `purchase_tax_code` (validated
  per side; null clears).
- **Documents:** `price_mode`, `no_vat_reason`, `invoice_kind`; lines `tax_code`. A line that takes its price from an
  earlier document must use that document's price mode. Minimum prices are compared on the net.
- **Sales:** a business that is not VAT-registered charges no VAT (OS) and issues an "invoice"; otherwise
  `tax_invoice` to a customer with a TRN, `simplified` without (setting `vat.simplified_for_unregistered`, R7).
- **Purchases:** recoverable → input VAT; SR-B → into the expense, refused on stock (R8); RC-S / RC-G → Dr input /
  Cr output VAT, the supplier owed the net (bill total = what is owed). The default purchase code is now SR (it was 0%).
- **Vouchers:** expense vouchers and debit notes take purchase codes, credit notes sales codes; blocked and reverse
  charge as above.
- **Old clients:** `vat_rate` alone still works (5 → SR; 0 → ZR on sales, OS on purchases, no code on vouchers).
- Migration 0015 (columns, check constraints, backfill of pilot rows with the posted-row guards paused).
- Tests: `test_tax_codes.py` (registry, rounding property test, resolve order, posting by treatment),
  `test_tax_api.py` (inclusive invoice, no-VAT reason, defaults, legacy input, invoice kind, return mode, unregistered
  business, reverse charge, blocked VAT, supplier default, inclusive stock value, RC return, vouchers). Test
  businesses (API and the sales e2e) are VAT-registered.
