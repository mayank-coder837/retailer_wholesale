# M1.13 — AI tool registry (plan)

Goal: an assistant that does what a person would do in the app — fills in a receipt from a sentence, answers "who owes
me?" — **without ever being able to do more than that person can**, and with every step on record.

Roadmap acceptance: "Received 5,000 cash from Ali Traders against INV-1093" → a draft receipt, allocated to that
invoice, awaiting confirmation. Proving tests: tool permission tests; an evaluation set (English and Arabic) with the
expected tool calls, run in CI; a `via_ai` audit test.

## Decisions (docs/architecture.md, product concept "AI Copilot v2")

1. **Tools, not SQL.** Each tool is one typed function over the existing services (rule 7: one door for writes); its
   input is a Pydantic model, which also gives the JSON schema a language model needs. No tool takes a business id,
   a tenant id or a user id from the caller: those come from the signed-in request.
2. **Risk tiers.** `read` and `draft` run at once. `commit` (post, cancel) never runs when asked: it is stored as a
   **pending action** and only runs when the person confirms it on screen, who must hold the permission *then*.
3. **The person's own permissions.** A tool names the permission it needs (or works it out from its input, e.g.
   `receipt.post` for a receipt, `purchase_bill.cancel` for a bill); a person without it gets a *denied* record, not
   an error page. The assistant has no permissions of its own.
4. **A full trace.** Table `ai_action`: who asked, the words they typed, the trace id shared by every step of one
   request, the tool, its risk, the arguments, the result or the reason it failed or was denied, and who confirmed.
   Everything the tools write is audited `via_ai = true`, `on_behalf_of` the person, with the `ai_trace_id`.
5. **The language model is a plug-in.** The provider (question T3) is not chosen, so the model sits behind a `Planner`
   interface: sentence → tool calls. Built now: a **rule-based planner** for the commonest sentences in English and
   Arabic (received / paid / who owes me), which is also what the CI evaluation set runs; and an `LlmPlanner` that
   answers "needs internet / not configured" until a provider and key are set. Everything else — tools, risk, audit,
   confirmation, screens — works the same whichever planner is used.

## Tools (first set)

| Tool | Risk | Permission | What it does |
| --- | --- | --- | --- |
| `find_party` | read | `customer.view` (`supplier.view` for suppliers) | Customers or suppliers matching a name |
| `get_open_bills` | read | `customer.view` / `supplier.view` | A party's unpaid invoices or bills |
| `get_receivables_ageing`, `get_payables_ageing` | read | `report.view` | What is owed, by age |
| `list_industry_packs` | read | `business.view` | The ready-made setups (textile, grocery…) |
| `create_draft_receipt` | draft | `receipt.create` | Money in from a customer, cash or bank, allocated to a named invoice (the rest on account) |
| `create_draft_payment` | draft | `payment.create` | Money out to a supplier, the same way |
| `post_voucher` | commit | `<type>.post` | Posts a draft voucher |
| `cancel_document` | commit | `<type>.cancel` | Cancels a posted document |
| `apply_industry_pack` | commit | `business.edit` | Applies a setup (units, attributes, settings) |

## Interfaces

- `GET /ai/tools` — the registry with risk, permission and input schema.
- `POST /ai/chat` `{business_id, text, lang}` — plan, run, return what happened and any pending actions.
- `POST /ai/call` `{business_id, tool, args}` — one tool directly (what a button on a draft uses).
- `GET /ai/actions`, `POST /ai/actions/{id}/confirm`, `POST /ai/actions/{id}/reject`.
- New permission resource `ai_assistant` (`view`, `create`) for Owner, Manager and Accountant (migration 0019 tops up
  existing tenants' roles).
- Web: **Assistant** page (type a request; see what was done, the drafts with their links, pending actions with
  Confirm / Reject), English and Arabic.

## Tests

Registry (every tool has a risk, a permission and a schema); the evaluation set (≥ 30 sentences en/ar → expected
calls, no network); the receipt flow end to end (draft allocated to INV-1, `via_ai` audit rows, trace); commit tools
return pending and run only on confirm; confirm needs the permission and the same person; reject; double confirm runs
once; a denied tool is recorded; read tools respect permissions; cross-tenant isolation of `ai_action`.

## Out of scope

Choosing and wiring a model provider (T3) and per-tenant metering; voice and photo entry; "ask your business"
analytics; anything that changes prices, refunds or overrides credit (tier `commit`, later).

## Built

- **Tools** (`app/modules/ai/tools.py`): `find_party`, `get_open_bills`, `get_receivables_ageing`,
  `get_payables_ageing`, `list_industry_packs` (read); `create_draft_receipt`, `create_draft_payment` (draft);
  `post_voucher`, `cancel_document`, `apply_industry_pack` (commit). Each calls an existing service; no tool takes a
  business, tenant, user, branch or account from the caller. A receipt takes the cash (or bank) account from the
  chart (code 1110 / 1120 first) and the head-office branch; money beyond the named invoice stays **on account**,
  never an advance by guess.
- **Registry** (`registry.py`): risk tier, permission (fixed or worked out from the input, e.g. `receipt.post` for a
  receipt), Pydantic input model (the JSON schema for a future model).
- **Service** (`service.py`): permission check → *denied* record; invalid arguments → *failed* record; read/draft run
  inside a savepoint (a refusal leaves nothing behind); commit tools become **pending** and run only on confirm, by the
  same person, who must hold the permission *at that moment*; a second confirm does not run it twice. Everything a tool
  writes is audited `via_ai`, `on_behalf_of` the person, client `ai`, with the trace id (also in `GET /audit`).
- **Planner** (`planner.py`): `RuleBasedPlanner` (received / paid / who owes me / what does X owe, English and Arabic,
  Arabic digits) and `LlmPlanner` ("not configured" until question T3 is decided). An unclear or ambiguous name
  becomes a question, not a guess.
- **API**: `GET /ai/tools`, `POST /ai/chat`, `POST /ai/call`, `GET /ai/actions`, `POST /ai/actions/{id}/confirm|reject`;
  permission resource `ai_assistant` (migration 0019 adds it to existing tenants' Manager and Accountant roles) and
  table `ai_action` with RLS.
- **Web**: Assistant page (`/assistant`) in English and Arabic: ask, see the draft with a link to open it, pending
  actions with Confirm / Reject, recent history.
- **Tests**: `tests/test_ai_api.py` (22: registry, receipt flow, on-account remainder, Arabic, payments, failures leave
  nothing, ambiguity, commit/confirm/reject/double confirm/other person/permission re-check, denial, cross-business,
  audit, trace), `tests/test_ai_evals.py` + `tests/ai_evals/cases.json` (41 sentences, en/ar), the `ai_action`
  isolation factory, `assistant.test.tsx` (5).

Open: the model provider (T3). Everything above works without one.
