# M0.3 — Roles and permissions (plan)

Goal: every endpoint checks a `resource.action` permission, scoped to a business or branch, through one
`require()` dependency. Acceptance (roadmap): a Salesperson scoped to Branch A cannot read Branch B data or post
vouchers.

## Permission registry (code, `app/core/permissions.py`)

- Codes are `resource.action`. Actions: `view, create, edit, delete, approve, post, cancel, reverse, export`, each
  resource listing only the actions that apply. Special codes: `price.override_min`, `credit.override`,
  `period.override_lock`.
- The registry already lists the Phase 1 resources (documents, vouchers, PDC, reports…), so default roles are
  complete from day one; endpoints for them arrive in Phase 1.
- Not stored in a table: the code is the source of truth, and the service rejects unknown codes.

## Tables (tenant tables: RLS, composite FKs, sync trigger, isolation factory)

| Table | Fields |
| --- | --- |
| `role` | name_en/_ar, description, system_key (`owner`, `manager`, `salesperson`, `warehouse`, `accountant`, `cashier`; null for custom), unique (tenant, system_key) |
| `role_permission` | role_id, permission_code; unique (role_id, permission_code) |
| `role_assignment` | membership_id, role_id, business_id (null = all businesses), branch_id (null = whole business); a branch requires its business, enforced by a composite FK to `branch(tenant_id, business_id, id)` |

Default roles are **seed data** (`apps/api/seeds/default_roles.json`, include/exclude patterns such as
`sales_invoice.*`), created for every new tenant at signup; the signup user gets Owner for the whole tenant.

## Scope rules

An assignment's scope is tenant-wide, one business, or one branch.

- `allows(code, business, branch)` — an action **on** that level: tenant-wide or same-business assignments act on
  any branch of it; a branch assignment only on that branch. Creating a business needs tenant-wide scope.
- `can_see(code, business)` — viewing a container: any assignment inside it is enough to see the business it
  belongs to (a Branch A salesperson still sees their business name).
- Lists are filtered to what the caller may see.
- Inactive membership → 403 `membership_inactive`; missing permission or out of scope → 403
  `permission_denied` (another tenant's ids stay 404 through RLS).

## API

| Endpoint | Permission |
| --- | --- |
| `GET /permissions` | `role.view` |
| `GET/POST /roles`, `GET/PATCH/DELETE /roles/{id}` | `role.view/create/edit/delete` (Owner role is read-only; system roles cannot be deleted; assigned roles cannot be deleted) |
| `GET /memberships`, `POST /memberships` (add a staff user with an initial password, like Tally users), `PUT /memberships/{id}/roles` | `membership.view/create/edit` |
| Existing tenancy endpoints | `business.*`, `branch.*`, `warehouse.*` with scope |

Guards: nobody can grant a role containing permissions they do not hold in that scope (no privilege escalation);
the tenant always keeps at least one tenant-wide Owner.

## Web

A minimal login form (access token in memory; the full shell comes in M0.5) and a **Roles** screen: roles list and
a permission matrix (resources × actions, en/ar labels via i18n) that the Owner can edit for non-Owner roles.

## Tests

- Permission matrix: role × endpoint (allowed / 403) for every default role.
- Scope: Branch-A salesperson sees only Branch A's warehouses, gets 403 on Branch B, cannot create branches;
  default Salesperson holds no voucher `post` permission (registry-level).
- Roles API: custom role CRUD, Owner immutable, unknown permission rejected, escalation blocked, last Owner kept.
- Isolation factories for the three new tables; signup seeds six roles with an Owner assignment.
- Web: roles screen renders the matrix and saves changes (Vitest, mocked API).
