# M2.1 — Cloud sync, browser access, multi-branch (plan)

Goal (roadmap): two branch PCs and a browser work on one tenant; numbers never clash; per-period checksums match
between each branch and the cloud after reconnecting. Design is fixed by ADR 0010 (transport, ownership,
numbering) and ADR 0011 (master-data conflicts). This plan only says how it is built and proved.

## Cloud host

Supabase Postgres 17 (project in region `ap-northeast-1`). Fine for pilots with **test data only**; ADR/architecture
require a UAE region before real customer data (PDPL, F7). The sync engine only needs a PostgreSQL URL, so moving
region later is a database move, not a code change. The database URL and password are the founder's to supply
(`SMARTBIZ_DATABASE_URL` for the cloud deployment); nothing in the repo holds them. Running our migrations against
Supabase needs a login that may create the app role and `FORCE ROW LEVEL SECURITY` tables (the `postgres` user can).

## How it is built, in slices (each one tested, pushed)

**a. Engine (no network).** `app/modules/sync`: read what a node has not pushed (`sync_outbox` rows whose
`node_id` is the node's own); apply a batch on the other side in outbox order, inside one transaction, with
`app.node_id` set to the *origin* node so the receiver's own trigger records it as foreign (a node never pushes
what it received, the cloud relays it to other branches); replay-safe through `node.last_push_seq`.
Rows are applied in SQL (`jsonb_populate_record`), never through Python floats, so money stays exact. The
receiver's own constraints re-validate everything (rule 4 balance trigger, immutability triggers, RLS).
Proved with **two real databases** (branch and cloud) in tests: replay, ordering, balance, relay to a second
branch, no echo.

**b. Transport.** `POST /sync/push`, `GET /sync/pull?since=`, node authentication (a node credential issued
at pairing, scoped to one tenant and node), a background pusher/puller on the branch PC (setting: cloud URL,
interval), status endpoint for the desktop app. Offline simply delays.

**c. Master-data conflicts (ADR 0011).** Per-field hybrid-logical-clock for master tables, same-field loser logged to
`sync_conflict` with both values; head-office wins on control fields; restore-losing-value action.

**d. Numbering across nodes.** Cloud/browser documents for a branch are drafts; the cloud refuses to number a
branch-owned series (already enforced by the series owner); posting a synced draft happens on the branch and the
number syncs back; the document shows "waiting for branch to number" until then.

**e. Integrity.** Per-period checksum endpoint (count and sums of journal lines and stock moves); a test that two
branches and the cloud agree after an offline stretch and reconnect; alert when a batch is rejected (sync stops for
that node, never skips data).

## Out of scope here

Browser/phone use of the cloud API (the same SPA against a cloud URL; needs hosting, domain and TLS: a deployment
task for the founder), S3 file storage adapter, e-invoicing and WhatsApp, multi-branch report screens beyond the
existing reports (they read the cloud's union already).

## Tests

Replay/idempotency, offline-for-a-week then reconnect, conflict per ADR 0011 rule, numbering across nodes, checksum
comparison, a rejected batch halts the node, cross-tenant isolation of everything the sync endpoints accept.

## Built (so far)

- **a. Engine** (`app/modules/sync/service.py`, migrations 0020 `sync_state`, 0021 outbox `txid`): a branch sends its own
  outbox rows after its saved position; a batch is cut only after a *finished* transaction and never splits one,
  so the receiver can check the whole of it. The receiver applies in SQL (`jsonb_populate_record`: amounts stay exact),
  in order, replay-safe through its saved position per node, with its own constraints deciding (balance trigger,
  immutability, row-level security). A refused batch changes nothing and the position does not move. The cloud
  records what it received as the sender's, so it is relayed to other branches and never echoed back. A member's
  user account travels with their membership (insert-only: a batch can add an account, never change one).
- **b. Transport**: `POST /sync/push`, `GET /sync/pull`, `GET /sync/checksum` (permissions `sync.post` / `sync.view`,
  Owner only: the Manager role is excluded because sync writes rows without going through the services).
  `CloudSync` (pull first, then push; offline only delays; a refused batch halts the PC) and a start-up daemon when
  `SMARTBIZ_CLOUD_URL`, `SMARTBIZ_SYNC_EMAIL`, `SMARTBIZ_SYNC_PASSWORD` are set. `SMARTBIZ_NODE_ROLE=cloud` makes the
  cloud write as its cloud node.
- **d. Numbering**: a branch's series are created owned by that branch's main PC, whoever asks first, so the cloud can
  never become the owner of one; a cloud-made draft is posted and numbered at the branch, and the number syncs back
  (tested end to end: the cloud answers `not_number_owner` until the branch has numbered it).
- **e. Checksums**: per month, count and totals of journal lines and stock moves; `differing_periods` names the month
  that disagrees. Tested: the branch is ahead before syncing, equal after.
- **c. Master-data conflicts** (migration 0022, `sync_merge_update`, `tests/test_sync_conflicts.py`): a three-way
  merge done in SQL. The capture trigger now stores, for an update, each changed column's value *before* the edit
  (`sync_outbox.changed`) and when the edit really happened (`edited_at`, kept as the row travels, so
  `touch_row` no longer stamps arrival time on synced rows). A receiver applies only the fields the sender changed:
  if its own value is still the old one the new one is taken; if the same field was changed on both sides it is a
  clash. The later edit wins (ties by node id); on a **control field** (price lists, accounts, units and
  conversion factors, tax-code overrides, costing settings) the cloud (head office) wins whatever the time. Every
  clash is written to `sync_conflict` with both values and both nodes. `GET /sync/conflicts` lists them and
  `POST /sync/conflicts/{id}/restore` puts the losing value back as a new edit by that person (so it wins
  everywhere). The per-field clock is read from the outbox, so there is no separate clock table. Limits: the
  wall clocks of the nodes are trusted (skew can flip a close call, but it is logged and restorable); an edit to
  an archived record is merged like any field (archiving is not undone by a later edit); duplicate creations are not
  merged (ADR 0011 rule 6); the conflict list has no screen yet and needs `sync.view` / `sync.post` (Owner only).
- **Live check:** `tests/test_live_cloud_sync.py` (opt-in with `SMARTBIZ_LIVE_CLOUD_DATABASE_URL`) ran green against
  the Supabase project: first upload, the branch's pusher, a browser edit pulled back, a clash decided, checksums
  equal.
- Tests: two real databases (branch and cloud) in `tests/test_sync_engine.py` and `tests/test_sync_transport.py`
  (replay, ordering, refusal, tenant isolation, relay without echo, offline then reconnect, halting, permissions,
  numbering across nodes, checksums, account takeover refused).

## Not built, and why (see open-questions R16 to R19)

- Several branches of one business posting stock (cost pool order) is an unanswered design question (R16).
- Enrolment of a PC set up before the cloud existed (R17), and the cloud deployment itself (host, domain, TLS,
  UAE region: R19).
