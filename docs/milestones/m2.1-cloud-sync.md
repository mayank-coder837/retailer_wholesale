# M2.1 — Cloud sync, browser access, multi-branch (plan)

Goal (roadmap): two branch PCs and a browser work on one tenant; numbers never clash; per-period checksums match
between each branch and the cloud after reconnecting. Design is fixed by ADR 0010 (transport, ownership,
numbering) and ADR 0011 (master-data conflicts). This plan only says how it is built and proved.

## Cloud host

Supabase Postgres 17 (project in region `ap-northeast-1`). Fine for pilots with **test data only**; ADR/architecture
require a UAE region before real customer data (PDPL, F7). The sync engine only needs a PostgreSQL URL, so moving
region later is a database move, not a code change. The database URL and password are the founder's to supply
(`SMARTBIZ_DATABASE_URL` for the cloud deployment); nothing in the repo holds them. Running our migrations against
Supabase needs a login that may create the app role and `FORCE ROW LEVEL SECURITY` tables (the `postgres` user can).

## How it is built, in slices (each one tested, pushed)

**a. Engine (no network).** `app/modules/sync`: read what a node has not pushed (`sync_outbox` rows whose
`node_id` is the node's own); apply a batch on the other side in outbox order, inside one transaction, with
`app.node_id` set to the *origin* node so the receiver's own trigger records it as foreign (a node never pushes
what it received, the cloud relays it to other branches); replay-safe through `node.last_push_seq`.
Rows are applied in SQL (`jsonb_populate_record`), never through Python floats, so money stays exact. The
receiver's own constraints re-validate everything (rule 4 balance trigger, immutability triggers, RLS).
Proved with **two real databases** (branch and cloud) in tests: replay, ordering, balance, relay to a second
branch, no echo.

**b. Transport.** `POST /sync/push`, `GET /sync/pull?since=`, node authentication (a node credential issued
at pairing, scoped to one tenant and node), a background pusher/puller on the branch PC (setting: cloud URL,
interval), status endpoint for the desktop app. Offline simply delays.

**c. Master-data conflicts (ADR 0011).** Per-field hybrid-logical-clock for master tables, same-field loser logged to
`sync_conflict` with both values; head-office wins on control fields; restore-losing-value action.

**d. Numbering across nodes.** Cloud/browser documents for a branch are drafts; the cloud refuses to number a
branch-owned series (already enforced by the series owner); posting a synced draft happens on the branch and the
number syncs back; the document shows "waiting for branch to number" until then.

**e. Integrity.** Per-period checksum endpoint (count and sums of journal lines and stock moves); a test that two
branches and the cloud agree after an offline stretch and reconnect; alert when a batch is rejected (sync stops for
that node, never skips data).

## Out of scope here

Browser/phone use of the cloud API (the same SPA against a cloud URL; needs hosting, domain and TLS: a deployment
task for the founder), S3 file storage adapter, e-invoicing and WhatsApp, multi-branch report screens beyond the
existing reports (they read the cloud's union already).

## Tests

Replay/idempotency, offline-for-a-week then reconnect, conflict per ADR 0011 rule, numbering across nodes, checksum
comparison, a rejected batch halts the node, cross-tenant isolation of everything the sync endpoints accept.
