# M0.4 — Platform services (plan)

Goal: the services every Phase 1 module relies on: audit, gap-free numbering, background jobs, idempotent writes,
attachments, settings and industry packs. Acceptance (roadmap): a replayed write returns the identical response;
numbers stay gap-free under concurrency and rollback; a released number is offered to the next document; packs
apply idempotently.

## 1. Audit log (CLAUDE.md rule 8)

- `audit_log` (tenant, **append-only**: the app role has no UPDATE/DELETE, and a trigger rejects them): at, actor,
  `via_ai`, `on_behalf_of`, `ai_trace_id`, client, request_id, action (`create, update, delete, post, cancel,
  reverse`), entity_type, entity_id, `changes` `{field: [old, new]}`, `snapshot` (full row, for delete/cancel).
- **Automatic**: an ORM flush hook records every create/update/delete of a tenant model, so no service can forget.
  Bookkeeping columns (`updated_at`, `created_by`…) are left out. Business actions (post, cancel, reverse) call
  `audit.record()` explicitly from Phase 1.
- Bulk SQL `UPDATE`/`DELETE` statements bypass the hook, so role-permission and assignment changes switch to ORM
  deletes.
- `GET /audit?entity_type=&entity_id=` with a new `audit.view` permission (Owner, Manager, Accountant).
- The Owner role now resolves to **every** registry permission at check time, so new codes never need a backfill
  for owners; a migration helper grants new codes to other default roles that their seed includes.

## 2. Numbering (ADR 0010, decisions A7/A12)

- `numbering_series`: branch, doc_type, fiscal year label, prefix, padding, `next_number`, `owner_node_id`.
- `released_number`: numbers freed by Cancel, offered to the next document; marked reused or left visible as
  CANCELLED.
- `numbering.allocate(...)` locks the series row (`SELECT … FOR UPDATE`) inside the posting transaction, so a
  rollback returns the number and concurrent posts queue: **gap-free, no duplicates**. Only the owner node may
  allocate (409 `not_number_owner` otherwise).
- Format: `INV-2026-00042` (prefix per document type, editable later).

## 3. Background jobs (ADR 0012)

- `outbox_event`: event_type, aggregate, payload, attempts, `available_at`, `locked_until`, last_error,
  dispatched_at, dead_at.
- `outbox.publish()` inside the business transaction; handlers registered with `@handler("event.type")`.
- In-process worker (asyncio task started by the API when `jobs_backend = inprocess`): claims a batch through a
  `SECURITY DEFINER` function (`FOR UPDATE SKIP LOCKED`, sets `locked_until`), then runs each event in its own
  tenant-scoped transaction and marks it dispatched in that same transaction. Failures back off exponentially;
  after 10 attempts the event is dead. A crashed worker's claim expires, so delivery is **at least once**.
- Celery dispatch for the cloud reuses the same handlers in M2.1.

## 4. Idempotent writes (CLAUDE.md rule 9)

- `idempotency_key` (tenant; user, key, request hash, response status/body/headers, expires after 24 h).
- Middleware for authenticated `POST/PUT/PATCH/DELETE` with an `Idempotency-Key` header:
  1. opens the request transaction and inserts the key row first; a concurrent duplicate waits on the unique index;
  2. the endpoint runs **in that same transaction**;
  3. on 2xx the response is stored in the same commit (atomic with the business change); on 4xx the business
     work is rolled back and the 4xx stored; on 5xx nothing is stored, so a retry runs again.
- Replays return the stored response with `Idempotent-Replayed: true`; the same key with a different request →
  409 `idempotency_key_reused`.

## 5. Attachments

- `attachment` (tenant): entity_type (a registry resource), entity_id, filename, content_type, size, sha256,
  storage_key. Files live in a local files folder (`SMARTBIZ_FILES_DIR`) behind a `Storage` interface; the S3
  adapter for the cloud comes with M2.1.
- `POST /attachments` (multipart, 20 MB, PDF/images/office/CSV/text), list, download, delete. Upload needs
  `<entity>.edit`, viewing `<entity>.view`.

## 6. Settings

- `setting` (tenant): scope (`tenant, business, branch, user`), scope_id, key, value. A typed registry in code
  defines each key's type, default and allowed scopes; effective value resolves user → branch → business →
  tenant → default.
- `GET /settings` (effective values), `PUT /settings/{key}`: `tenant.edit` for tenant/business/branch scope,
  any member for their own user-scope keys.

## 7. Industry packs

- Seed files `seeds/industry_packs/*.json`: general trading, textile, hardware, electronics, grocery. Each holds
  units, attributes, custom fields and settings defaults.
- `industry_pack_application` records pack, version and applied sections per business. Section appliers are
  registered by modules: M0.4 applies **settings**; units/attributes/custom fields are recorded as pending and
  applied when M1.1/M1.2 register their appliers. Re-applying the same version changes nothing.
- `GET /industry-packs`, `POST /businesses/{id}/industry-pack` (`business.edit`).

## Tests

Audit old→new and append-only; idempotency replay, conflict, concurrent duplicates and stored 4xx; concurrent
numbering with rollbacks (contiguous, no duplicates); released-number reuse; outbox handler success, retry with
backoff and reclaim after an expired lock; attachment upload/download/isolation; settings resolution; pack
validation and idempotent re-apply; isolation factories for every new table.
