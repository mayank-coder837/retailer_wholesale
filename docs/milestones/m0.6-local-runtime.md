# M0.6 — Local runtime (plan)

Goal: one Windows installer that runs a branch fully offline. The main PC runs PostgreSQL 17 and the API as
Windows services; other office PCs pair with it over the LAN. No Docker on customer PCs (ADR 0008).
Acceptance (roadmap): on a clean Windows PC, install → onboard → log in; a second PC on the LAN pairs and logs in;
unplugging the network changes nothing; an update with a failing migration rolls back.

## Pinned components (downloaded and checksum-verified at build time, never committed)

| Component | Version | Notes |
| --- | --- | --- |
| PostgreSQL | 17.11 Windows x64 binaries (EDB) | `bin`, `lib`, `share` only; pgAdmin, StackBuilder, docs stripped |
| Python | CPython 3.12.15 standalone (python-build-standalone) | API dependencies installed from `uv.lock` |
| WinSW | 2.12.0 | Runs the API as a Windows service |

`apps/desktop/scripts/prepare-runtime.mjs` assembles `apps/desktop/build/runtime/` (pgsql, python, winsw, api code,
migrations, seeds); electron-builder ships it as `resources/runtime`.

## Layout on a customer PC

| Path | Content |
| --- | --- |
| `C:\ProgramData\SmartBizOS\config.json` | mode (`main` / `client`), ports, LAN on/off, active runtime version, paired main PC |
| `…\runtime\<version>\` | API + Python + PostgreSQL binaries of that version (services point here) |
| `…\pgdata\` | PostgreSQL data (ACL: Administrators, SYSTEM, NetworkService) |
| `…\files\`, `…\backups\`, `…\tls\`, `…\logs\` | attachments, `pg_dump` files, self-signed certificate, service logs |
| `…\secrets\db.bin` | database password, DPAPI (LocalMachine) encrypted, ACL-restricted |

Ports: PostgreSQL **5440** on 127.0.0.1 only (never on the LAN); API **8710**.

## Runtime manager (Electron main process, `apps/desktop/src/runtime/`)

Small, idempotent steps over an injectable command runner, so they are unit-tested with a fake runner and
integration-tested for real on Windows:

1. `setupMain` — directories and ACLs → password (DPAPI) → `initdb` (scram-sha-256, UTF8) → `postgresql.conf`
   (port 5440, `listen_addresses = 127.0.0.1`) → register PostgreSQL service with `pg_ctl register` (it drops
   admin rights itself; NetworkService) → start → create database, owner login and the app role → self-signed TLS
   certificate → register the API service (WinSW, NetworkService) → `alembic upgrade head` → start → wait for
   `/health/db`. Re-running skips finished steps.
2. **LAN** — on: API binds `0.0.0.0` with TLS and a Windows Firewall rule (Private profile, port 8710); off: API
   binds 127.0.0.1 and the rule is removed.
3. **Pairing** (client mode) — the main PC shows an 8-character code (10 minutes, single use). The office PC
   enters the main PC's address and the code, sends a random nonce, and checks the API's
   `HMAC(code, nonce ‖ certificate fingerprint)` against the fingerprint it actually saw in the TLS handshake,
   then pins that certificate. A relay in the middle sees a different certificate, so the proof fails.
4. **Backups** — `pg_dump -Fc` nightly (in-process job on the API) and before every update; keep 14; restore
   stops the API service, `pg_restore --clean`, starts it again.
5. **Upgrade** — the installer copies the new runtime to `runtime\<new>`, then: backup → stop API → migrate with
   the new code → switch the service to `runtime\<new>` → start → health. Any failure: restore the backup, switch
   back to `runtime\<old>`, start, report. The main PC's UI is served by its API, so UI and API versions always
   match after a rollback.

A `processes` mode runs the same steps with PostgreSQL and the API as child processes (developers, CI, tests).

## App changes

- API: serves the built SPA (`SMARTBIZ_WEB_DIR`, same origin, no CORS); optional TLS; `POST /pairing/challenge`;
  nightly backup job; pg_dump path from settings.
- SPA: with no override, the API is the page's own origin.
- Electron: first launch asks "main PC" (elevated setup) or "office PC" (pairing); main PC loads
  `http://127.0.0.1:8710`, office PC loads `https://<main-pc>:8710` with the pinned certificate; preload gains
  runtime actions (backup now, list, restore, LAN on/off, show pairing code) for the main PC.
- Installer: NSIS hooks run `--runtime-setup` / `--runtime-upgrade` / `--runtime-uninstall` (data kept unless the
  user ticks "remove data").

## Tests

- Unit (node:test): every runtime step with a fake runner, including idempotent re-runs, port collision,
  pairing proof and rollback decisions.
- Integration (Windows, `processes` mode, real binaries): setup → `/health/db` → sign up → backup → change data →
  restore → data back; an upgrade with a deliberately failing migration rolls back and the old version answers.
- CI `windows-latest` job: build the runtime, install the services, health check, log in, uninstall.
- Pairing endpoint tests in the API suite.

## Out of scope

Code signing (decision D3: before the first customer release), auto-discovery of the main PC on the LAN (enter
the address), cloud sync (M2.1).
