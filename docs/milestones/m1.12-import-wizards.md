# M1.12 — Import wizards (plan)

Goal: a trader moving off Tally or Excel gets their customers, suppliers, items, opening balances, unpaid
invoices and stock into the app in an afternoon, and can **prove** the books came across right.

Roadmap acceptance: the imported trial balance matches the source; `opening_balance_equity` nets to 0. Proving
tests: fixture imports (Excel, CSV, Tally XML); reconciliation tests; re-importing the same file changes nothing.

Rule 7 applies: an import is just another client of the services. Masters go through `parties`, `catalog` and
`accounting` services; opening balances are posted as **journal vouchers** and an **opening stock document** with
the same checks, numbering, period lock and audit as a hand-typed one. The import module owns only the work
record (the batch), the file readers and the reconciliation.

Five pull requests:

| PR | Scope |
| --- | --- |
| **M1.12a** Engine and masters (API) | Module `imports`: file readers (CSV, Excel), column mapping, batch lifecycle, import of customers and suppliers, items, accounts |
| **M1.12b-1** Opening balances and bills (API) | Opening trial balance, outstanding bills per customer / supplier, reconciliation report, undo |
| **M1.12b-2** Opening stock (API) | New stock document type `opening_stock`, the opening stock import, the inventory line of the reconciliation |
| **M1.12c** Tally (API) | Tally XML reader feeding the same rows; fixtures |
| **M1.12d** Screens | Import wizard in Settings: choose what, download a template, upload, match columns, check, import, reconciliation page; e2e |

## How an import works (all kinds)

1. **Upload** — `POST /imports` (multipart: business, kind, file). The file is stored (files folder / S3) with its
   SHA-256; a *batch* row (`import_batch`) records who, when, what and the file hash. The reply lists the columns
   found, a few sample rows, and a **suggested mapping** (see below).
2. **Check** — `POST /imports/{id}/check` with the chosen mapping and options. Nothing is written except the
   mapping on the batch. The reply has one line per file row: `new`, `exists` (already in the books, skipped) or
   `error` (what is wrong and in which column), plus totals.
3. **Import** — `POST /imports/{id}/commit`. The file is read again and checked again, then everything is written in
   **one transaction**: any problem and nothing is imported (**all or nothing** — the founder never has to guess
   which half went in). The reply is the result, also kept on the batch.

- **Idempotent.** Committing a batch twice returns the first result. Uploading a file whose hash was already
  imported for that business and kind says so (`duplicate_of`) and refuses to import it again. Masters are matched
  to what exists (parties by TRN then name; items by SKU; accounts by code) and **skipped, never overwritten**, so
  an overlapping second file adds only what is new. Opening balances can be imported once per business; a mistake
  is fixed with **Undo** (M1.12b), which cancels the vouchers it made.
- **Permissions.** New resource `import` (`import.view`, `import.create`, `import.post`); Owner and Manager get it
  through `*`, Accountant is added in the seed. Creating masters also needs the master's own permission
  (`customer.create`, `product.create`, `account.create`) — an import never lets anyone do more than the screens.
- **Audit.** Every row created is audited by its own service; the batch is audited too, and the audit client of an
  import is `import`.
- **Limits.** `settings.max_upload_bytes`; at most 20,000 data rows per file; Excel read in read-only mode.

### Reading files

- **CSV** — UTF-8 (with or without BOM); falls back to Windows-1256 then Windows-1252 (what Excel on a UAE PC
  saves as "CSV"); delimiter `,` `;` or tab sniffed.
- **Excel** (`.xlsx`) — first sheet, first non-empty row = headers; formulas read as their last calculated value.
  New dependency `openpyxl` (read-only, `data_only`).
- **Numbers** are read exactly, never as floats: `1,234.50`, `(500.00)`, `1 000,5`, Arabic-Indic digits
  `١٢٣٫٥`, a trailing `Dr` / `Cr` (Tally), blank = 0. An Excel number cell goes through its shortest text form.
- **Dates** — real Excel dates, ISO `2026-03-31`, and **day first** `31/03/2026`, `31-03-2026`, `31 Mar 2026`
  (UAE order; a month-first reading is never guessed).
- **Text** is trimmed; Arabic and English names are kept as typed. Formula-looking cells (`=`, `+`, `@`, leading
  `-` on text) are kept as text and never evaluated — and are escaped again if a file is ever exported back.

### Matching columns

Each kind has fixed **fields** (name, TRN, opening debit…) with English and Arabic header synonyms
(`Party Name`, `Ledger`, `اسم العميل`…). The upload reply suggests the column for each field by matching headers
after trimming, lower-casing and removing punctuation and diacritics; the user can change any of it in the wizard.
This is deterministic matching — the AI-assisted mapping of the concept document arrives with M1.13 (the AI calls
the same endpoints).

### Templates

`GET /imports/templates/{kind}?lang=en|ar` downloads a CSV with the headers and one example row, so a customer
with no export can start from it.

## M1.12a — engine and masters (API)

- Module `app/modules/imports`: `readers.py` (CSV / Excel → header + rows, pure), `values.py` (number, date,
  text parsers, pure), `mapping.py` (synonyms, suggestion), `kinds/` (one file per kind: fields, row check, row
  apply), `service.py` (batch lifecycle), `router.py`, `models.py` (`import_batch`).
- **Table `import_batch`** (migration 0016, RLS + cross-tenant test): business, kind, status
  (`uploaded → checked → committed | undone`; a failed import rolls back, so there is no failed state), file name, file key, sha256, size, mapping (JSONB),
  options (JSONB), counts (JSONB), result (JSONB), committed_at / by.
- **Kinds in this PR**
  - `parties` — customers and suppliers: name (en, ar), kind (customer / supplier / both), TRN, phone, email,
    address, city, emirate, credit days, credit limit. Created through `parties.service.create_party` (+ customer
    / supplier profile). Existing = same TRN, else same English name (case-insensitive).
  - `products` — items: name (en, ar), SKU, barcode, product type (stock / service / non-stock), base unit, selling
    price (the base unit's price; cost comes from bills and opening stock), barcode, sales / purchase tax code,
    batch / expiry flags. Created through `catalog.products.create_product`;
    unknown unit or tax code = a row error; SR-B on a stock item refused as on the screen (rule R8).
  - `accounts` — extra ledgers on the chart: code, name (en, ar), parent code, type. Through the accounting chart
    service (`account.create`); system accounts and roles are never touched.
- Tests: pure tests for readers and parsers (including a Hypothesis round-trip: any `Decimal` formatted in any of
  the supported styles reads back exactly); API tests with fixture files (CSV in each encoding, `.xlsx`, Arabic
  names), the check / commit / re-commit / duplicate-file flows, all-or-nothing (one bad row imports nothing),
  skipped-existing, permissions, cross-tenant read test for `import_batch`, audit client.

## M1.12b — opening balances (API)

Posting rule 35, in two pull requests. **M1.12b-1** is the trial balance, the outstanding bills and the
reconciliation; **M1.12b-2** is opening stock.

Every opening kind shares these options: the **opening date** (the day the old books stop, usually the last day of
the old fiscal period; required) and the **branch** the vouchers belong to (default: the head office).

- The opening date must have its fiscal year created (only the current and next year are created on their own, so
  for a past date create that year first) and its period must be open. Both are checked when the file is checked,
  not only when it is imported, and say what to do.
- Everything is posted as **journal vouchers** (`JV`, numbered in the opening date's year) through
  `accounting.post_voucher`: the same checks, numbering, period lock and audit as one typed by hand, and Cancel
  works. They are narrated "Opening balances imported from <file>". Needs `journal.create` and `journal.post` on top
  of the import permissions.

### `opening_balances` — the trial balance

Columns: account (code, or name in either language), debit, credit — or one **balance** column with a Dr / Cr mark or
a sign (debit positive). Each row is a line; one extra line per voucher puts the difference against
`opening_balance_equity`, so every voucher balances by construction (rule 4). A voucher holds up to 150 accounts.

- **Control accounts** — receivables, payables, stock — are not posted from the trial balance (a journal may not touch
  them without a party or a stock move). Their rows are kept as the **expected** totals for the reconciliation; the
  real balances come from the party bills (this PR) and the opening stock (M1.12b-2). Question R13.
- Rows that are refused with the row and column named: an unknown account ("import the account first"); a group
  (subtotal rows of a Tally export must be removed — a group would double count); an archived account;
  `opening_balance_equity` itself; a system-only account; an account listed twice; a negative amount; both a debit and
  a credit on one row. A row with nothing in it is *skipped* (counted apart, not an error).
- The file does **not** have to balance: the difference lands in `opening_balance_equity` and is shown, in words, by
  the check and the reconciliation (it should be 0.00 — a trial balance always balances; if it does not, the file is
  incomplete). The check shows total debit, total credit, the difference and the expected control totals.
- Once per business: while one trial balance is imported (and not undone) another is refused (`opening_already_imported`),
  whatever the file. Undo makes room for the next.

### `party_bills` — outstanding invoices and bills

Columns: party (code, TRN or name), reference (the invoice or bill number), invoice date, due date, amount, and
optionally the side (Dr / Cr) and the ledger (customer / supplier) for a party that is both.

- A customer's invoice is a **debit** on the receivable control account; a supplier's bill a **credit** on payables.
  An amount with a minus sign, or a mark opposite to the normal one (Cr on a customer, Dr on a supplier), is an
  **advance / credit balance** instead (an `advance` bill, shown apart on the ageing).
- One journal line per bill, with a `new_ref` (or `advance`) allocation, so the bill is open bill-wise, with the
  control account balanced by `opening_balance_equity`. A voucher holds up to 150 bills.
- The invoice date is kept as the bill's date (small addition: optional `bill_date` on a new-reference allocation,
  migration 0017, never after the voucher's date). Due date: as given, else invoice date + the party's credit days
  (customers) or payment terms (suppliers), else the invoice date.
- A bill of the same party and reference already open is *skipped* (so two files — customers and suppliers, or a
  corrected file — never double count). The same reference on another side or ledger is a different bill.
- Imported bills carry no VAT split (question R12). Paid-off bills are not imported.

### Reconciliation report

`GET /imports/reconciliation?business_id` — for the business's imported trial balance (not undone):

- **Accounts:** every row of the file with its balance on the opening date in the books and the difference; control
  accounts show the books' balance coming from bills / stock against the file's figure.
- **Totals:** the file's total debit and credit, the books' total, and the **balance of `opening_balance_equity`**.
- **Verdict:** *ties* when every difference and the equity balance are 0.00; otherwise the list of what differs and
  by how much. Read from the ledgers (the trial balance as at the opening date), not from the file.
- Rows of the file are remembered on the batch (`result.expected`) so the report can be produced at any time.

### Undo

`POST /imports/{id}/undo` (`import.post`, plus `journal.cancel`): cancels the vouchers the batch created
(`documents.service.cancel`: only while the period is open, and refused while something later depends on the
bills), marks the batch `undone`, and the same file can be imported again. All or nothing as well.

### Tests (M1.12b-1)

Hand-computed fixture (a small trading business): trial balance of 9 accounts incl. control rows, 3 customer and 2
supplier bills (one an advance) → every account balance, every bill with its original date and due date, the party
ledgers, the ageing, `opening_balance_equity` = 0 and the verdict *ties*; a fixture that does not tie (equity ≠ 0,
reported by how much); refusals (unknown / group / archived / equity / duplicate / negative / both sides); no
fiscal year and closed period; once-per-business; bill skipped when already open; undo and re-import; pure parsing
of balance marks; a property test (random balanced trial balance → imported balances equal the file, equity 0,
every voucher balances).

### M1.12b-2 — opening stock

- **`opening_stock`** kind: item (SKU / barcode), warehouse, quantity, unit, unit cost (or total value), batch and
  expiry for batch items. A new stock document type **`opening_stock`** (prefix `OS`, migration for the
  document-type check) posts `opening` stock moves at the given cost with `opening_balance_equity` as the counter
  account (rules 5, 6; negative or missing cost refused). It is a document like any other: Cancel / Reverse work.
- The reconciliation's inventory line compares the file's figure with the stock valuation.

## M1.12c — Tally

Tally exports to XML (and to Excel/CSV, which M1.12a already reads). `readers.py` gains a Tally XML reader that maps
the export to the **same rows** as the Excel kinds, so everything after reading is shared:

- Ledger masters (`LEDGER`): name, parent group → customer / supplier / account type, TRN (`PARTYGSTIN` / tax
  registration number), opening balance with its Dr / Cr sign, bill allocations (`BILLALLOCATIONS.LIST`: name,
  date, credit period, amount) → `parties`, `accounts`, `opening_balances`, `party_bills`.
- Stock items (`STOCKITEM`): name, base units, opening quantity / rate / value → `products`, `opening_stock`.
- Parsing uses `defusedxml` (new dependency: Tally files are untrusted input; plain `xml` is open to entity
  expansion attacks). Tally's Dr/Cr sign convention differs by version and export — the reader is tested against
  fixtures built from the documented structure; **a real export from the founder's Tally is needed before
  customers rely on it** (open question R14).
- Group mapping (Sundry Debtors → customers, Sundry Creditors → suppliers, Bank Accounts / Cash-in-Hand → cash and
  bank, Duties & Taxes → VAT, Direct / Indirect Income / Expenses → income / expense) is a seed table
  (`seeds/import/tally_groups.json`), not code.

## M1.12d — screens

Settings → **Import data**: a step list (what to import, in the order masters → accounts → opening → stock):

1. Pick the kind (cards with one line each, and the recommended order).
2. Download the template / choose the file (CSV, Excel, Tally XML).
3. Match columns (each field with a dropdown of the file's columns, pre-filled).
4. Check: counts of new / existing / errors; an error table with row number, column and message; "Fix the file and
   check again" — nothing is imported until it is clean.
5. Import: confirmation with the totals (for opening balances: the date and totals in words), then the result.
6. **Reconciliation** page (from Reports and from the wizard's end): tie-out table and the OBE verdict, green when 0.

English and Arabic (RTL), screen tests, and an e2e: import customers, items and an opening trial balance, bills and
stock from fixture files; the reconciliation shows 0.00; the trial balance screen shows the file's balances.

## Questions for the accountant (added to `docs/open-questions.md`; defaults built and marked)

- **R11** — Opening date and income / expense accounts. A trial balance taken mid-year has income and expense
  balances as well. Default: they are imported as given, dated the opening date, so profit to date is right for the
  year; the P&L for a period starting the next day shows only new activity. Alternative: close them to retained
  earnings first. Which do you want?
- **R12** — VAT on imported outstanding invoices. Imported bills carry no VAT split: their VAT was reported in the old
  system's returns, so the VAT return here excludes them. The VAT payable / receivable balance comes in through the
  trial balance. Confirm.
- **R13** — Control accounts. Receivables, payables and inventory in a trial balance are **not** posted from it;
  they come from the imported bills and stock, and the reconciliation shows any difference (it stays in
  `opening_balance_equity` rather than being forced). Confirm, or should a difference go to a suspense account?
- **R14** — Tally Dr / Cr sign and group mapping were built from Tally's documented XML; please send one real export
  (masters with bills, and stock items) so the reader can be checked against it.

## Out of scope for M1.12

Importing posted history (past invoices, vouchers, stock movements — opening balances only, as Tally migrations
usually do); updating existing masters from a file; PDC (cheques in hand are keyed in on the cheque screen);
AI-assisted column mapping (M1.13); other accounting packages (Zoho, QuickBooks).

## Built — M1.12a

Module `app/modules/imports`, migration 0016 (`import_batch`, row-level security, isolation test), endpoints
`GET /imports/kinds`, `GET /imports/templates/{kind}`, `POST /imports`, `GET /imports`, `GET /imports/{id}`,
`POST /imports/{id}/check`, `POST /imports/{id}/commit`; permission resource `import` (view, create, post; the
Accountant role has it, Owner and Manager through `*`).

- **Kinds:** `accounts`, `parties`, `products`, as planned. Existing = skipped, never changed. A party is recognised
  by TRN, then by name in either language; an item by SKU (product or variant); an account by code.
- **Per-row permissions for parties:** a file of customers needs `customer.create`; a row that makes a supplier needs
  `supplier.create`. A person without it sees that row marked "You may not create suppliers" and nothing is imported.
- **Party codes:** typed codes are created first; the rest are numbered once for the whole file (C0001, S0001, P0001),
  so the two never collide and a large file does not re-read every code for each party.
- **Files:** CSV (UTF-8, Windows-1256, Windows-1252; `,` `;` or tab) and `.xlsx`. Read as it streams: 20,000 data
  rows, 200 columns, 200 MB unzipped; an Excel sheet is read until 1,000 empty rows in a row. Parsing runs off the
  event loop so other PCs on the LAN are not held up.
- **Numbers and dates:** exact decimals (property test: any amount, written in any supported style, reads back
  exactly; probed once with a deliberately wrong parser). Day-first dates; two-digit years 00-69 are 20xx and 70-99
  are 19xx; years outside 1990-2100 are refused.
- **Audit:** everything an import creates is audited with client `import`.
- **Not done here (by design):** opening balances, bills and stock (M1.12b), Tally XML (M1.12c), screens (M1.12d).
  The check results carry a stable `code` and `field` for every problem; the screens translate the message from
  them (rule 10) — the English `message` is the fallback. A 20,000-row import runs inside one request.

Tests: API 575 before the review fixes; the import tests are `test_import_values.py` (parsers, Hypothesis),
`test_import_readers.py` (files, column matching) and `test_imports_api.py` (the whole flow, permissions, tenant
isolation, audit).
