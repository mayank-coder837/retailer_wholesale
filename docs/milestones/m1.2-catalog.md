# M1.2 — Catalog (plan)

Goal: a trader can set up what they sell — products with their units (1 roll = 50 m, 1 carton = 24 pcs), colour
and width variants, barcodes per unit, categories, brands and their own fields — and scanning a barcode finds the
exact variant and unit.

Roadmap acceptance: the textile pack creates a fabric with colour/width variants and roll/metre units; a barcode
scan finds variant + unit. Proving tests: custom-field validation; barcode uniqueness per tenant; isolation tests.

Delivered as two pull requests (merge after every change): **M1.2a** the catalog API, **M1.2b** the screens.

## Model (all tenant tables: forced RLS, audit, sync capture, composite `(tenant_id, …)` foreign keys)

| Table | Columns | Rules |
| --- | --- | --- |
| `category` | `parent_id`, `name_en/_ar`, `archived_at` | Tree; no cycles; names unique among siblings |
| `brand` | `name_en/_ar`, `archived_at` | Name unique per tenant |
| `attribute` | `code`, `name_en/_ar` | Colour, width, size… (packs add them); `code` unique per tenant |
| `attribute_value` | `attribute_id`, `value_en/_ar`, `sort` | Unique per attribute (by English value) |
| `custom_field_def` | `entity_type` (`product, variant, party, document`), `key`, `label_en/_ar`, `data_type` (`text, number, decimal, date, bool, select, multiselect`), `options`, `required` | `key` unique per entity type |
| `product` | `sku`, `name_en/_ar`, `description`, `product_type` (`stock, service, non_stock`), `category_id`, `brand_id`, `base_unit_id`, `track_batch`, `track_expiry`, `track_serial`, `custom_fields` (JSONB), `archived_at` | `sku` unique per tenant; base unit fixed once created (stock is kept in it) |
| `product_unit` | `product_id`, `unit_id`, `factor_to_base` NUMERIC(19,6), `is_purchase_default`, `is_sales_default` | The base unit is always a row with factor 1; factor > 0, exact (L3) and fixed once created; one purchase and one sales default per product |
| `product_attribute` | `product_id`, `attribute_id` | Which attributes a product varies by |
| `variant` | `product_id`, `sku`, `custom_fields`, `archived_at` | Every product has ≥ 1 variant (one default variant when it has no attributes); `sku` unique per tenant; stock, prices and lines will reference variants |
| `variant_attribute_value` | `variant_id`, `attribute_id`, `value_id` | One value per attribute per variant; no two variants with the same combination |
| `barcode` | `variant_id`, `unit_id`, `code`, `kind` (`ean13, code128, internal, scale`) | `code` unique per tenant; the unit must be one of the product's units; EAN-13 check digit verified |

Deferred: `default_tax_code_id` (tax codes, M1.10); `sale_price` / `min_price` on product units (pricing, M1.3).

**Product units.** A product's units may cross families (1 roll = 50 m). When a unit is of the same family as the
base unit, the standard factor is suggested (1 cm = 0.01 m) but the trader may set another (a carton of 24 pcs is a
count unit with standard factor 1). Conversions on lines go through `uom.to_base` with the product unit's factor:
exact, never rounded (L3).

**Variants.** Creating a product with attributes and chosen values generates every combination (colour × width =
4 variants for 2 × 2); more can be added later. A variant SKU defaults to the product SKU plus the values
(`FAB-001-RED-44IN`); Arabic-only values fall back to a number.

**Custom fields.** Values live in `custom_fields` JSONB on product and variant, validated by the service against the
definitions: type, required, select options; unknown keys refused.

## API

Permissions: products, variants, units of a product and barcodes — `product.view/create/edit/delete`; categories,
brands and attributes — `product.create/edit`; custom field definitions — `tenant.edit` (account configuration).

- `GET/POST /categories`, `PATCH /categories/{id}` (rename, move, archive; no cycles)
- `GET/POST /brands`, `PATCH /brands/{id}`
- `GET/POST /attributes`, `POST /attributes/{id}/values`
- `GET/POST /custom-fields`, `PATCH /custom-fields/{id}`
- `GET /products?q=&category_id=&brand_id=&include_archived=` (search SKU, names, barcodes), `POST /products`,
  `GET /products/{id}` (units, attributes, variants, barcodes), `PATCH /products/{id}`
- `POST /products/{id}/units`, `PATCH|DELETE /products/{id}/units/{unit_code}` (not the base unit)
- `POST /products/{id}/variants`, `PATCH /variants/{id}`
- `POST /products/{id}/barcodes` (a code, or generate an internal EAN-13 in the in-store `2…` range),
  `DELETE /barcodes/{id}`, `GET /barcodes/{code}` → product, variant, unit, factor to base
- Industry packs: the `attributes` and `custom_fields` sections now apply (by code / key; existing ones untouched).

## Screens (M1.2b)

Inventory → Products: list with search (name, SKU, barcode); new-product form (names en/ar, SKU, type, category,
brand, base unit, extra units with factors, attributes and values with a variant preview, custom fields); product
page (units, variants, barcodes). Settings → Catalog: units, categories, brands, attributes, custom fields. English
and Arabic.

## Tests

- Acceptance: apply the textile pack; create a fabric (base m, roll = 50 m, colour {red, blue} × width {44 in,
  58 in}) → 4 variants; add a barcode to red/44 in for the roll; scanning it returns that variant, the roll and 50.
- Custom fields: each data type, required, options, unknown key; barcode uniqueness per tenant (and the same code in
  two tenants); EAN-13 check digit; unit must belong to the product; no duplicate variant combinations; category
  cycles refused; base unit and factors immutable; permissions (a salesperson may view, not create); isolation
  factories for every new table; pack attributes/custom fields applied once.
- Screens: Vitest for list, form (variant preview, unit factors) and product page, English and Arabic.
